# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

`Instances` is a small .NET library that wraps `System.Diagnostics.Process` with a fluent, three-tier API for running external processes synchronously or asynchronously, with events, cancellation, and captured output. It is published as the [`Instances` NuGet package](https://www.nuget.org/packages/instances/).

The `Instances` library targets **netstandard2.0** with **C# 8** (`LangVersion=8`) and nullable reference types enabled. Do not use language/runtime features newer than C# 8 in the library project. The two test projects target **net10.0**.

## Commands

```bash
# Build everything
dotnet build

# Run all tests (matches CI)
dotnet test

# Run tests with coverage (as CI does)
dotnet test --collect "XPlat Code Coverage" --verbosity normal

# Run a single test by name
dotnet test --filter "Name=VerifyKillStopsProcess"

# Run tests whose fully-qualified name matches a substring
dotnet test --filter "FullyQualifiedName~Cancellation"
```

Packaging is not part of a normal build; `dotnet pack Instances -c Release -o <dir>` produces the `.nupkg`. Don't add `GeneratePackageOnBuild` back — it makes `dotnet pack` skip the build, which fails with NU5026 on a clean tree (that broke the first automated release).

## Releasing

A release is a bump of `<PackageVersion>` in `Instances/Instances.csproj` (commit message convention: "Bump version"). Once that lands on `main` and the test matrix passes, the `release` job in `.github/workflows/ci.yml` packs and pushes to nuget.org, then creates the `vX.Y.Z` tag and a GitHub Release. The job only runs when `<PackageVersion>` is not yet on nuget.org (checked against the flat-container index), so pushes that don't bump the version are no-ops and re-runs are safe.

Release notes are generated by the release job, not written by hand: the subjects of non-merge commits since the previous `v*` tag that touched `Instances/`, minus the "Bump version" commit. The same list goes into the package's `PackageReleaseNotes` and the GitHub Release body. This means **the subject of any commit touching `Instances/` is user-facing copy**; test- and CI-only commits are excluded by the path filter. The csproj deliberately has no `<PackageReleaseNotes>`; a local `dotnet pack` produces a package with empty notes. Two details of the job are load-bearing: the checkout uses `fetch-depth: 0` because `git describe` needs the tags and the history back to the previous one, and the notes are handed to `dotnet pack` as an environment variable (MSBuild reads env vars as properties) because `-p:` splits on `;` and cannot carry newlines.

Publishing authenticates with NuGet Trusted Publishing (`NuGet/login@v1`, OIDC → 1-hour API key); there is no stored secret. The policy lives on nuget.org under the `rosenbjergsoftworks` profile and is keyed on repo owner `rosenbjerg`, repo `Instances`, workflow file `ci.yml` — renaming the workflow file breaks publishing until the policy is updated.

## Architecture

The public surface is three layers over one core class. All three ultimately call `ProcessArguments.Start()` → `ProcessInstance`.

- **`Instance`** (`Instance.cs`) — static facade, the shortest form. `Start` / `Finish` / `FinishAsync` take a path + args (or `ProcessStartInfo`) and optional output/error handlers.
- **`ProcessArguments`** (`ProcessArguments.cs`) — the configurable entry point. Holds the `ProcessStartInfo`, exposes `IgnoreEmptyLines` and `DataBufferCapacity`, and the `Exited` / `OutputDataReceived` / `ErrorDataReceived` events. `Start()` is where the process is actually configured and launched.
- **`ProcessInstance`** (`ProcessInstance.cs`) — the live process handle returned as `IProcessInstance`. Owns waiting, killing, input, and output buffers.

`ProcessArgumentsExtensions` adds `StartAndWaitForExit[Async]` convenience methods.

### How `Start()` configures a process

`ProcessArguments.Start()` always forces these on the `ProcessStartInfo`: `CreateNoWindow`, `UseShellExecute=false`, and redirection of **all three** standard streams (in/out/err). `EnableRaisingEvents=true`. It then begins async reads (`BeginOutputReadLine` / `BeginErrorReadLine`). A `Win32Exception` for a missing executable is translated into `InstanceFileNotFoundException`.

### The exit handshake (the central concurrency design)

`ProcessInstance` coordinates three `TaskCompletionSource<bool>`: `_mainTask`, `_stdoutTask`, `_stderrTask`. This exists to guarantee **all output is captured before exit is reported**:

1. `BeginOutputReadLine`/`BeginErrorReadLine` push lines through `ReceiveOutput`/`ReceiveError` → `AddData`. A **null** `Data` is the stream's EOF marker and completes `_stdoutTask` / `_stderrTask`.
2. The process's `Exited` event (`ReceiveExit`) does **not** complete immediately — it awaits `Task.WhenAll(_stdoutTask, _stderrTask)`, then raises the public `Exited` event and completes `_mainTask`.
3. `WaitForExitAsync` awaits `_mainTask`, so it only returns after both streams have drained.

When editing `ProcessInstance`, preserve this ordering — completing `_mainTask` or raising `Exited` before both stream tasks finish would surface truncated output. The continuation completes `_mainTask` in a `finally` so a throwing `Exited` subscriber cannot leave `WaitForExitAsync` hanging, and it is pinned to `TaskScheduler.Default` because a sync `WaitForExit()` call can be the thread that raises `Exited`, and `ContinueWith` would otherwise inherit that caller's scheduler.

### Output buffering

`AddData` enqueues into `Queue<string>` buffers. `DataBufferCapacity` (default `int.MaxValue`) makes them ring buffers: once over capacity, the oldest lines are dequeued — so with a small capacity you keep only the **last** N lines. `IgnoreEmptyLines` drops empty lines. `OutputData`/`ErrorData` return read-only snapshots.

### Cancellation and kill

`WaitForExitAsync(cancellationToken)` registers a callback that kills the process if `_process.HasExited` is false.

The `CancellationTokenRegistration` is disposed both on process exit and in `Dispose`. On exit it is disposed **inside the `ContinueWith` continuation** (after the stream tasks drain), **not** synchronously in `ReceiveExit`: `ReceiveExit` runs inside the BCL's `Process.RaiseOnExited`, which holds `lock(process)`, and `CancellationTokenRegistration.Dispose()` blocks until any in-flight cancellation callback finishes — and the callback's `_process.HasExited` needs that same lock, so disposing there deadlocked (issue #10). The continuation runs on the thread pool after the lock is released. Do not move the registration disposal back into `ReceiveExit`. `Kill()` and the sync `WaitForExit()` translate an already-exited process into `InstanceProcessAlreadyExitedException`. `GetResult()` returns exit code `-100` if the process has not actually exited, which is why repeated `Kill()`/`WaitForExit()` calls return a consistent result.

## Tests

- NUnit 4. Tests live in `Instances.Tests/Tests.cs`.
- Tests shell out to the real `dotnet` CLI (e.g. `dotnet --list-runtimes`, `dotnet --help`, `dotnet run --project Nopes` to force an error), so **`dotnet` must be on PATH** and behavior can depend on the installed SDK output.
- `Instances.Tests.WaitingProgram` is a tiny console app whose entire body is `Console.Read()` — it blocks until it receives stdin. Tests that exercise input/kill/cancellation use it. The `[OneTimeSetUp]` (`Prepare`) publishes it to `./waiting-program/` before those tests run.
- `WaitForExitAsyncDoesNotDeadlockWhenCancellationRacesExit` is the regression test for issue #10. The deadlock window is a few microseconds per attempt, so it is a **volume-driven stress test**: it races short-lived processes against a cancellation timed near their natural exit, in oversubscribed parallel batches, for a fixed budget, and fails if any `WaitForExitAsync` never completes. The short-lived process comes from `GetShortLivedProcessArguments`, which branches by OS (`sleep` on Unix, `powershell Start-Sleep` on Windows) rather than using `dotnet`, because the race needs a precise, cheap, tunable process lifetime. It passes for the full budget on the fixed library and fails (usually within ~1–2 s) on the buggy one.
