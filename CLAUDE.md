# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

`Instances` is a small .NET library that wraps `System.Diagnostics.Process` with a fluent, three-tier API for running external processes synchronously or asynchronously, with events, cancellation, and captured output. It is published as the [`Instances` NuGet package](https://www.nuget.org/packages/instances/).

The `Instances` library targets **netstandard2.0** and **net8.0** with **C# 8** (`LangVersion=8`) and nullable reference types enabled. Do not use language features newer than C# 8 in the library project. The net8.0 build exists for `Process.Kill(entireProcessTree: true)`, which backs `KillEntireProcessTree`; code that needs it goes behind `#if NET5_0_OR_GREATER`, and on netstandard2.0 `Start()` throws `PlatformNotSupportedException` when the option is set. The two test projects target **net10.0**.

## Commands

```bash
# Build everything
dotnet build

# Run all tests (matches CI)
dotnet test

# Run tests with coverage (as CI does)
dotnet test --collect "XPlat Code Coverage" --verbosity normal

# Run a single test by name
dotnet test --filter "Name=VerifyKillStopsProcess"

# Run tests whose fully-qualified name matches a substring
dotnet test --filter "FullyQualifiedName~Cancellation"
```

Packaging is not part of a normal build; `dotnet pack Instances -c Release -o <dir>` produces the `.nupkg`. Don't add `GeneratePackageOnBuild` back — it makes `dotnet pack` skip the build, which fails with NU5026 on a clean tree (that broke the first automated release).

`dotnet pack` runs package validation: both builds are compared with the published package named by `<PackageValidationBaselineVersion>`, and an API break fails the pack, and with it the release job. A minor or patch release keeps the baseline; a major release that breaks the API on purpose raises it (or adds a suppression file). Restore downloads the baseline into the global packages folder, the only place the validation task looks. If a NuGet fallback folder (`NUGET_FALLBACK_PACKAGES`) already holds that version, restore skips the download and the pack fails with "Package … instances.X.Y.Z.nupkg not found"; unset the variable and restore with `--force`.

## Releasing

A release is a bump of `<Version>` in `Instances/Instances.csproj` (commit message convention: "Bump version"). `<Version>` sets both the package and the assembly version; the CI `version` job reads the derived `PackageVersion` property. Once the bump lands on `main` and the test matrix passes, the `release` job in `.github/workflows/ci.yml` packs and pushes to nuget.org, then creates the `vX.Y.Z` tag and a GitHub Release. The job only runs when that version is not yet on nuget.org (checked against the flat-container index), so pushes that don't bump the version are no-ops and re-runs are safe.

Release notes are generated by the release job, not written by hand: the subjects of non-merge commits since the previous `v*` tag that touched `Instances/`, minus the "Bump version" commit. The same list goes into the package's `PackageReleaseNotes` and the GitHub Release body. This means **the subject of any commit touching `Instances/` is user-facing copy**; test- and CI-only commits are excluded by the path filter. The csproj deliberately has no `<PackageReleaseNotes>`; a local `dotnet pack` produces a package with empty notes. Two details of the job are load-bearing: the checkout uses `fetch-depth: 0` because `git describe` needs the tags and the history back to the previous one, and the notes are handed to `dotnet pack` as an environment variable (MSBuild reads env vars as properties) because `-p:` splits on `;` and cannot carry newlines.

Publishing authenticates with NuGet Trusted Publishing (`NuGet/login@v1`, OIDC → 1-hour API key); there is no stored secret. The policy lives on nuget.org under the `rosenbjergsoftworks` profile and is keyed on repo owner `rosenbjerg`, repo `Instances`, workflow file `ci.yml` — renaming the workflow file breaks publishing until the policy is updated.

## Architecture

The public surface is three layers over one core class. All three ultimately call `ProcessArguments.Start()` → `ProcessInstance`.

- **`Instance`** (`Instance.cs`) — static facade, the shortest form. `Start` / `Finish` / `FinishAsync` take a path + args (or `ProcessStartInfo`) and optional output/error handlers.
- **`ProcessArguments`** (`ProcessArguments.cs`) — the configurable entry point. Holds the `ProcessStartInfo`, exposes `IgnoreEmptyLines`, `DataBufferCapacity` (negative values throw) and `KillEntireProcessTree`, and the `Exited` / `OutputDataReceived` / `ErrorDataReceived` events. `Start()` is where the process is actually configured and launched.
- **`ProcessInstance`** (`ProcessInstance.cs`) — the live process handle returned as `IProcessInstance`. Owns waiting, killing, input (`SendInput[Async]`, `CloseInput`), and output buffers.

`ProcessArgumentsExtensions` adds `StartAndWaitForExit[Async]` convenience methods. `ProcessInstanceExtensions.CloseInput` puts `CloseInput` on `IProcessInstance` as an extension method, because a new interface member would break implementations outside the library; it throws `NotSupportedException` for other implementations. New members of `IProcessInstance` follow the same pattern until a major release.

### How `Start()` configures a process

`ProcessArguments.Start()` always forces these on the `ProcessStartInfo`: `CreateNoWindow`, `UseShellExecute=false`, and redirection of **all three** standard streams (in/out/err). `EnableRaisingEvents=true`. It then begins async reads (`BeginOutputReadLine` / `BeginErrorReadLine`). A `Win32Exception` with native error code 2 (file not found) is translated into `InstanceFileNotFoundException`; the code is checked, not the message, which is localized. Any failure to start disposes the `Process`.

### The exit handshake (the central concurrency design)

`ProcessInstance` completes `_completion` (a `TaskCompletionSource<IProcessResult>`) only after `_stdoutTask` and `_stderrTask` are done. This guarantees **all output is captured before exit is reported**:

1. `BeginOutputReadLine`/`BeginErrorReadLine` push lines through `ReceiveOutput`/`ReceiveError` → `AddData`. A **null** `Data` is the stream's EOF marker and completes `_stdoutTask` / `_stderrTask`.
2. The process's `Exited` event (`ReceiveExit`) completes nothing itself: it continues `Task.WhenAll(_stdoutTask, _stderrTask)` with `Complete()`.
3. `Complete()` runs once (guarded by `Interlocked.Exchange`), builds the result once (`GetOrCreateResult`, cached in `_result`), raises the public `Exited` event, then completes `_completion`. `WaitForExitAsync` awaits `_completion`.

When editing `ProcessInstance`, preserve this ordering — completing `_completion` or raising `Exited` before both stream tasks finish would surface truncated output. `ReceiveExit` must stay asynchronous: the BCL raises `Exited` inside `Process.RaiseOnExited`, which holds `lock(process)`, so blocking there deadlocks against anything else that needs the lock (issue #10). The continuation is pinned to `TaskScheduler.Default` because a sync `WaitForExit()` call can be the thread that raises `Exited`, and `ContinueWith` would otherwise inherit that caller's scheduler.

Exceptions from `Exited` subscribers are swallowed so they cannot keep `_completion` from completing. While `Exited` is raised, `_completion` is not complete yet, so `FinishedResult` also returns `_result` when the thread-static `_raisingExited` is this instance: `Kill()`, `WaitForExit()` and `WaitForExitAsync()` called from an `Exited` handler return the result instead of waiting on a completion the handler itself holds up.

### Output buffering and handler errors

`AddData` enqueues into `Queue<string>` buffers under a lock on the queue, so `OutputData`/`ErrorData` (read-only snapshots) are safe to read while the process runs. `DataBufferCapacity` (default `int.MaxValue`) makes them ring buffers: once over capacity, the oldest lines are dequeued — so with a small capacity you keep only the **last** N lines. `IgnoreEmptyLines` drops empty lines.

An exception from an `OutputDataReceived`/`ErrorDataReceived` handler is caught (on the BCL's reader thread it would crash the app), stored (at most 100), and reading continues. `WaitForExit[Async]` rethrows it once the process is done: the single exception with its original stack, or an `AggregateException` for several.

### Cancellation and kill

`WaitForExitAsync(cancellationToken)` (`WaitOrKillAsync`) registers a callback that only completes a local `TaskCompletionSource`, and disposes the registration as soon as the process completes or the token fires. The callback never touches the `Process`, so it cannot need `lock(process)`, which is what deadlocked in issue #10. On cancellation it kills the process and waits up to `KillGracePeriod` (5 s) for the normal completion; if the streams have not ended by then (a child process inherited the output pipe and still holds it), it waits for the process itself to exit and calls `Complete()` without the stream tasks. Cancellation returns the result; it does not throw `OperationCanceledException`.

`Kill()` returns the finished result if there is one; otherwise it kills, waits up to `KillGracePeriod` for the process to exit (else throws `InstanceException`), and returns the real exit code with the output read so far. `KillProcess()` tolerates a process that has already exited. With `KillEntireProcessTree` (net8.0 build) it kills the tree, and falls back to killing only the process if that throws `AggregateException`.

After `Dispose()`, `Kill()` and the sync `WaitForExit()` throw `InstanceProcessAlreadyExitedException`, as they did when the disposed `Process` threw; `WaitForExitAsync` and the input methods throw `ObjectDisposedException`. `SendInput[Async]` after `CloseInput()` throws `InvalidOperationException`.

## Tests

- NUnit 4. Tests live in `Instances.Tests/Tests.cs`.
- Tests shell out to the real `dotnet` CLI (e.g. `dotnet --list-runtimes`, `dotnet --help`, `dotnet run --project Nopes` to force an error), so **`dotnet` must be on PATH** and behavior can depend on the installed SDK output.
- `Instances.Tests.WaitingProgram` is a tiny console app driven by its first argument: with none it blocks on `Console.Read()` until it receives stdin; `lines N` prints N lines; `echo-stdin` echoes stdin to its end (for `CloseInput`); `sleep MS` sleeps; `child MS [wait]` starts a sleeping copy of itself that inherits the output pipe (for `KillEntireProcessTree` and the kill grace period). Tests that exercise input/kill/cancellation use it. The `[OneTimeSetUp]` (`Prepare`) publishes it to `./waiting-program/` before those tests run.
- `WaitForExitAsyncDoesNotDeadlockWhenCancellationRacesExit` is the regression test for issue #10. The deadlock window is a few microseconds per attempt, so it is a **volume-driven stress test**: it races short-lived processes against a cancellation timed near their natural exit, in oversubscribed parallel batches, for a fixed budget, and fails if any `WaitForExitAsync` never completes. The short-lived process comes from `GetShortLivedProcessArguments`, which branches by OS (`sleep` on Unix, `powershell Start-Sleep` on Windows) rather than using `dotnet`, because the race needs a precise, cheap, tunable process lifetime. It passes for the full budget on the fixed library and fails (usually within ~1–2 s) on the buggy one.
